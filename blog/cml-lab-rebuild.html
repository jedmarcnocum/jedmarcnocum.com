From Packet Tracer to Cisco Modeling Labs: Starting My CCNA Lab Rebuild

Why I’m rebuilding my CCNA lab

While studying for the CCNA, I used Cisco Packet Tracer alongside Jeremy’s IT Lab course on Udemy. As I worked through the lessons, the individual lab exercises sometimes felt disconnected because each focused on a specific topic. To see the bigger picture and connect the dots, I began building my own topology rather than treating every topic as a separate exercise. I expanded that topology as I learned more.

That project now covers VLAN segmentation, trunking, inter-VLAN routing, RSTP, EtherChannel, OSPF, HSRP, DHCP, DNS, NAT/PAT, ACLs, IPv4/IPv6, wireless, voice/QoS, and access-layer security controls. It gave me a solid foundation and helped me pass the CCNA, but I did not want the project to end after the exam.

I wanted to keep building in an environment closer to a Cisco lab workflow: creating nodes, wiring interfaces, opening device consoles, and troubleshooting the platform itself. That is why I decided to begin rebuilding the project in Cisco Modeling Labs (CML).

Setting up CML in VMware Workstation

I imported the CML virtual appliance into VMware Workstation and attached Cisco’s reference-platform ISO. The server booted successfully, but CML still needed access to the reference-platform content before Cisco IOL node types could be used in a lab.

The first problem: CML could not detect the reference platform

CML asked for the reference-platform ISO even though I had selected it in VMware, reporting that it could not find a CD-ROM device. The missing part was the connection state of the virtual CD/DVD device: selecting an ISO file is not enough if the device is not connected to the running virtual machine.

I shut CML down cleanly, returned to VMware’s CD/DVD settings, and enabled both Connected and Connect at power on . After starting the virtual machine again, CML could see the mounted ISO and the Copy Refplat process began successfully.

It was a useful reminder that a lab problem is not always a Cisco configuration problem. Sometimes the issue is one layer below—in this case, how VMware presented storage to the CML appliance.

Getting into the CML interface

Once the reference platform had been copied, I confirmed that CML had imported the Cisco IOL node definitions. I then created a new lab and kept the first test deliberately small: 

              IOL router  ─────────  IOL-L2 switch

The goal was not to recreate the whole CCNA topology yet. I wanted to verify the basic workflow first:

  • Add Cisco nodes to a CML canvas.
  • Create a link and select interfaces.
  • Start the nodes and open each console.
  • Confirm that the Cisco CLI is accessible.

First successful CML test

After creating the link, I started both nodes and opened their consoles. The CLI loaded successfully, confirming that the reference platform, node images, lab wiring, and console access were all working.

This small test was an important milestone: I had moved from an existing Packet Tracer portfolio to a working CML environment where I can rebuild the same design progressively.

What I learned from the initial setup

  1. Confirm what the error was actually saying: CML could not find a CD-ROM device.
  2. Check VMware virtual hardware instead of assuming the selected ISO was connected.
  3. Correct the CD/DVD connection settings.
  4. Re-run the reference-platform copy process.
  5. Verify the result by adding IOL nodes, connecting them, starting them, and opening their consoles.

Seeing a “copy complete” message is useful, but a successful router-and-switch test proves that the lab is ready to use.

What’s next

The next step is to rebuild a compact version of the existing core topology within CML-Free’s five-node limit, feature by feature rather than all at once.

  • VLANs and trunking.
  • EtherChannel and spanning-tree behaviour.
  • Inter-VLAN routing, OSPF, and HSRP.
  • DHCP, DNS, NAT, ACLs, and IPv6.
  • Troubleshooting and verification evidence.

Later, I plan to integrate a separate Windows Server and Active Directory lab so I can practise cross-discipline troubleshooting—for example, determining whether a client issue is caused by VLAN assignment, DHCP, DNS, routing, ACLs, or Active Directory.

Why I’m documenting the build

This blog is part of my networking portfolio. I want to show the process behind the project: what I was trying to achieve, what went wrong, how I checked it, and how I verified the fix.

The original Packet Tracer project remains available on GitHub . The next post will cover the first switching stage and the design choices I make as I translate the existing lab into the new environment.
