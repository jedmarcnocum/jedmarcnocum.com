CML Lab Rebuild, Part 2: The Five-Node Foundation

Hello there! As promised, we're now continuing with Part 2 of our CML rebuild blog series! As planned, I have added five nodes in our CML lab, added the links, and named the devices in this format: AREA-DEVICE_TYPE-NUMBER.

Why these five nodes?

These five nodes form a compact HQ design with a collapsed core: the distribution switches provide Layer 2 toward access and Layer 3 toward the edge.

Node Node type Why it is in the topology
HQ-ASW-01IOL-L2 Layer 2 switchRepresents the access layer where clients connect. Its two separate uplinks to the distribution pair establish the foundation for redundant access paths, VLAN trunks, and Rapid-PVST.
HQ-DSW-01IOL-L2 multilayer distribution switchForms one half of the collapsed core. It will provide SVIs and inter-VLAN routing, then share gateway and spanning-tree duties with HQ-DSW-02 as the lab grows.
HQ-DSW-02IOL-L2 multilayer distribution switchCreates a second distribution path without inventing a larger campus too early. Later, the pair will load-balance HSRP and Rapid-PVST roles by VLAN rather than using a permanent active/backup design.
HQ-EDGE-01IOL routerCreates the Layer 3 boundary between HQ and the simulated provider. It gives the distribution layer routed upstream links now and becomes the IPv4 PAT point in a later security phase.
ISP-01IOL routerActs as an isolated provider simulation, so the lab can test a proper external routing boundary without placing the ISP inside HQ OSPF or relying on the public Internet.

Keeping five nodes for now lets Part 2 concentrate on the switching and dual-stack foundation. The next phases add dynamic routing and HSRP, then external endpoints and services; the broader multi-access, voice, and wireless campus arrives later in the series.

Base device configuration

With the five nodes named and linked, I applied a consistent starting configuration to each device. This establishes local administrative access, protects privileged mode, enables SSH, and disables the unused HTTP services before the network-specific configuration begins.

Base configuration
ip domain name hq.jmcn.test
username labadmin privilege 15 secret <secret>
enable secret <secret>
crypto key generate rsa modulus 2048
ip ssh version 2
no ip http server
no ip http secure-server

line console 0
 exec-timeout 30 0
 logging synchronous

line vty 0 6
 login local
 transport input ssh
 exec-timeout 10 0

The secret values are intentionally omitted here. Each device uses its own secure values, while the shared baseline keeps console sessions tidy and permits remote management through SSH only.

These local accounts are a lab baseline; centralized AAA and management filtering are later hardening work.

Device and interface map

While connecting each link, I am also adding interface descriptions. I did not practise this in my original CCNA lab, but I want to build the habit early: clear descriptions make the cabling map easier to understand, review, and troubleshoot.

One thing I learned while studying for the CCNA is to use the available show commands to reach the goal in front of me, whether that means debugging an issue or simply working out which interface connects to which device.

While writing these descriptions, I did not rely on the CML GUI to read the interface labels on each link. Instead, I used LLDP to confirm the local interface, neighbouring device, and remote port before documenting the connection. I know that GUI's and automation are useful and faster to use, but I want to keep my manual CLI skills sharp. :)

Beyond being a best practice, descriptions keep the intent of each interface clear even when a discovery protocol is unavailable. They also make a mismatched or rogue connection easier to spot when the documented link does not match the device actually connected, and they provide useful context for future alerts and logging.
